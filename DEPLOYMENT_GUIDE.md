# GitAlong — deployment guide

Order matters: **database → backend → clients**. The new clients depend on
columns, views and RPCs added by the migrations.

## 0. Rotate the leaked GitHub OAuth secret (do this first)

The GitHub OAuth App client secret is in the public git history of both
repositories (see `docs/AUDIT.md` → *Action required*).
1. GitHub → Settings → Developer settings → OAuth Apps → GitAlong →
   **Generate a new client secret**, then delete the old one.
2. Supabase → Authentication → Providers → GitHub: paste the new secret.
3. Never put the secret in `.env`, docs or the website. Only Supabase needs it.

## 1. Database (Supabase)

1. **Back up** production first: Dashboard → Database → Backups, or `pg_dump`.
2. Apply the migrations in `supabase/migrations/` in filename order:
   - CLI: `supabase link --project-ref <ref>` then `supabase db push`
   - or paste each file into the SQL editor, oldest first.
3. Check the result:
   - `select * from public.public_profiles limit 1;` runs and has no `email` column.
   - Table editor → `matches` has `pair_key` and `last_message_sender_id`.
   - Database → Triggers lists `on_auth_user_created`, `on_users_clamp_last_active`,
     `on_swipe_server_time`, `on_swipe_match`, `on_match_deleted`,
     `on_message_before_insert`, `on_message_after_insert`, `on_message_after_delete`.
   - `select public.get_my_progress(0);` works when run as a signed-in user
     (in the SQL editor it raises "not authenticated", which is expected).
4. Before applying, run the same migrations locally against a copy of the
   legacy schema: `cd supabase/tests && npm install && npm test`.

> **Compatibility:** after the migration, **old app and website builds can no
> longer write `users` directly or create matches**, because those were the
> security holes. Ship the new clients together with the migration.

Auth settings:
- Providers → GitHub enabled.
- URL Configuration → Site URL: `https://gitalong.app`.
- URL Configuration → Redirect URLs: `app.gitalong://login-callback/`,
  `https://gitalong.app/**`, `https://www.gitalong.app/**`,
  `https://gitalong-preview.vercel.app/**`, `http://localhost:5173/**`,
  `http://127.0.0.1:5173/**`. When the page a user signs in from isn't on this
  list, Supabase sends them to the Site URL instead, so a Site URL that
  doesn't serve the site breaks sign-in.
- Don't list domains you don't control (`gitalong.vercel.app` belongs to
  someone else): Supabase would hand session tokens to that site.
- GitHub OAuth App callback URL: `https://<project>.supabase.co/auth/v1/callback`.
- DNS: `gitalong.app` needs `A @ 76.76.21.21` (and `CNAME www cname.vercel-dns.com`)
  at the registrar (Name.com) and must be added to the Vercel project `gitalong`.

## 2. Backend (Render, Docker)

`render.yaml` at the repo root defines the service (`rootDir: backend`).

1. Render → New → Blueprint → select the repo, or update the existing
   `gitalong-backend` service.
2. Set the environment variables (see `backend/.env.example`):
   - `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`
   - `SUPABASE_JWT_SECRET`: only if your project still uses the legacy HS256 JWT secret
   - `GITHUB_TOKEN`: a fine-grained token with public read access (raises the rate limit)
   - `ALLOWED_ORIGINS`: website origins, comma-separated
   - `ADMIN_RETRAIN_SECRET`: generated by the blueprint
3. Deploy, then check `GET https://<service>/api/v1/health` →
   `{"status":"ok","database":"connected"}`.

Notes:
- The container runs as a non-root user and trusts proxy headers, so client IPs
  and per-user rate limits work behind Render's load balancer.
- On the free plan the first request after idling can take tens of seconds.
  The apps only use the backend for recommendations and GitHub sync, so core
  loops aren't affected. Use a paid instance for launch.
- ML re-ranking: once there are enough likes *and* dislikes, call
  `POST /api/v1/admin/retrain-ml` with `X-Admin-Secret`, then set
  `ML_RANKING_ENABLED=true`.
- Metrics: `GET /api/v1/admin/metrics` with `X-Admin-Secret`.

## 3. Mobile app

1. `.env` (bundled into the app, so public values only):
   ```env
   SUPABASE_URL=https://<project>.supabase.co
   SUPABASE_ANON_KEY=<anon key>
   BACKEND_URL=https://gitalong-backend.onrender.com
   ```
2. `flutter pub get && flutter test`.
3. Android: create a keystore and `android/key.properties`
   (`storeFile`, `storePassword`, `keyAlias`, `keyPassword`), then
   `flutter build appbundle --release --obfuscate --split-debug-info=build/symbols`.
   Beta APKs go on GitHub Releases (https://github.com/GitAlong-App/gitalong/releases),
   which the website links to.
4. iOS: set the bundle identifier and signing in Xcode, then `flutter build ipa --release`.
   Before submitting, confirm App Review requirements for third-party sign-in
   (Sign in with Apple, guideline 4.8). Block/report and in-app account deletion
   are already implemented.

## 4. Website

Deployed on Vercel from `GitAlong-App/GitAlong-Website` (see that repo's
README). Set `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` and `VITE_BACKEND_URL`,
and make sure its origin is listed in the backend's `ALLOWED_ORIGINS`.

## 5. After launch

- **Reports:** check `public.reports where status = 'open'` daily until a
  moderation view exists.
- **Errors:** add Sentry (or similar) to the app, website and backend.
- **Supabase advisors:** Dashboard → Advisors. `public_profiles` is
  intentionally a definer view (it hides `email` and applies blocks). Review any
  other findings.
